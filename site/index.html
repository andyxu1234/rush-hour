Overview

项目概览

背景、方案与关键工程决策

纯 TypeScript · Canvas 2D 一套代码 → H5 / 微信小游戏 独立开发（玩法 / 求解器 / 渲染 / 工程化）

一个 6×6 棋盘的滑块解谜：场上有横竖不同长度的车辆，只能沿自身轴向滑动， 目标是把红色小车从右侧第 3 行的出口开出去。计步口径刻意选「滑动次数」 而非「滑动格数」—— 一次滑 3 格仍算 1 步，这让最优解常常需要先倒车再前进。

工程上的核心目标是同一套代码同时产出网页版与微信小游戏版。为此把整个项目切成 四层：纯逻辑内核（规则 / 求解器 / 状态机 / 存档）不依赖任何平台； 渲染层只画像素、不碰宿主 API；所有平台能力（画布、存储、音频、图片、广告、分享） 收敛到一个冻结的 Platform 接口后面，两端各给一份实现。 这使得换端只改一行装配代码，复用率约 95%。

关卡不是手摆的，而是由 Python 参考求解器反向游走生成 + BFS 校验最少步数， 并用一套「去重指纹」剔掉等价局面。为避免两套实现漂移，CI 里会拿 TypeScript 求解器 复算 Python 算出的每一关指标（最少步数、滑动格数、难度、状态数），逐关比对。

核心工作与亮点

  • 自研 BFS 求解器：求最少步数、剩余步数、以及「当前最优下一步」用于提示；关卡难度由求解器结果反推，而非人工标注
  • 计步模型只有一份事实来源 —— 棋盘状态一律由走子序列重放得出，因此「撤销 = 弹栈」「存档 = 存 moves」「防作弊 = 服务端重放」三件事共用同一份数据，永远不会互相漂移
  • 双端渲染零分叉：微信小游戏没有 DOM、禁用 eval，因此渲染层被 ESLint 强制禁止出现 window / document / wx
  • 真实的自动化验证：跨语言一致性校验 + 132 个单测 + Playwright 端到端（含带手指抖动的真实触摸手势），一键质量门同时守住类型、测试、包体与产物红线
  • 卡通车辆贴图与代码绘制双路径：贴图缺失或加载失败时自动回落为矢量色块车，素材永远不可能让游戏跑不起来

Gameplay

玩法与设计亮点

规则极简，但决策空间不小

🚗

拖拽即滑动

按住车沿自身轴向拖动，前后画出半透明虚影提示可占位范围；松手吸附到最近合法格。非法方向播放短促回弹，不计步。

🎯

提示只给一步

提示基于求解器算出的当前最优下一步，只揭示该动哪辆车、往哪个方向滑几格，不直接给完整解法 —— 保留思考乐趣。

⭐

星级锚定理论最少步数

三星 = 达到 par（BFS 算出的最少步数），两星 = par + 2 以内，完成即得一星。结算时给出「比最少步数多 N 步」的明确对照。

↩️

撤销 / 重开 / 断点续玩

撤销以走子序列弹栈实现，与存档、防作弊共用同一份数据。切后台或退出后再次进入，会自动重放上次的走子继续玩。

📈

难度由求解器反推

不做人工难度标注：关卡的最少步数、状态空间大小与分支度由求解器算出，据此分档为入门 / 简单 / 中等 / 困难。

🧩

关卡程序化生成

Python 参考实现从终局反向游走生成局面，再用求解器校验「可解且步数落在目标区间」，同时用去重指纹剔掉等价局面。

Architecture

技术架构

四层单向依赖，平台能力全部收口到一个冻结接口后面

Core · 纯逻辑

  • 棋盘模型与合法性判定
  • BFS 求解器（最少步数 / 提示）
  • 对局状态机 + 星级计算
  • 存档结构与其逐项清洗

Render · 渲染与交互

  • Canvas 2D 绘制（车辆 / 棋盘 / HUD）
  • 布局几何：绘制、命中、断言三处同源
  • 拖拽手势与轻点判定
  • 10 个屏幕与导航栈

Platform · 宿主抽象

  • 画布 / 存储 / 音频 / 图片
  • 指针事件统一为 pointer 语义
  • H5 实现：DOM + localStorage
  • 小游戏实现：wx.* API

Quality · 质量门

  • 132 个单测（core + render）
  • 跨语言一致性：TS 求解器复算 Python 结果
  • Playwright 端到端（含真实触摸手势）
  • 包体与产物红线自动断言
